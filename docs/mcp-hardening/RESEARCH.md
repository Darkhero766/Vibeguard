# MCP and application-security research — 2026-11-24

This is a source-based engineering assessment, not a claim that every referenced tool has been installed or benchmarked here. Versions and capabilities were checked against current upstream materials on 2026-11-24.

## MCP protocol and SDK

MCP's 2026-07-28 revision introduces a stateless request model, per-request protocol/client metadata, optional `server/discover`, deterministic/cacheable list responses, MRTR, extension mechanisms, and authorization changes. The current implementation advertises this revision and retains older handshake-era compatibility. A hand-written protocol surface needs wire-schema and conformance tests; method-level unit tests alone cannot establish conformance. The official conformance project supports server/client scenarios and wire-schema validation, including version-specific requirements. Sources: [MCP 2026-07-28 release](https://blog.modelcontextprotocol.io/posts/2026-07-28/), [official conformance framework](https://github.com/modelcontextprotocol/conformance).

The official TypeScript SDK v2.4.0 was released 2026-10-23. It splits client/server/core packages and has separate migration guidance for v1-to-v2 package changes and the 2026 stateless protocol. The current server is a deliberately small custom stdio implementation, with legacy support and a set of local authorization/snapshot semantics. Migrating only to follow the release would be a material protocol rewrite, not a mechanical dependency upgrade; it is not justified without first running official conformance against both the legacy and modern wire paths and proving equivalent authorization, cancellation and error behavior. Revisit if the project needs SDK-managed structured content or more MCP features. Sources: [SDK 2.4.0 release](https://github.com/modelcontextprotocol/typescript-sdk/releases), [SDK package map](https://github.com/modelcontextprotocol/typescript-sdk/blob/main/docs/get-started/packages.md), [migration guide](https://github.com/modelcontextprotocol/typescript-sdk/blob/main/docs/migration/index.md).

## Codex integration

OpenAI's current docs support MCP servers in Codex CLI and IDE; users can add a remote server with `codex mcp add ... --url ...`, list configured servers with `codex mcp list`, or configure a local server in `~/.codex/config.toml`. This confirms Codex remains an MCP client. Reports about removing Codex-as-server functionality do not imply client support was removed. VibeSane's documented stdio server config is consistent with the local command/args/env shape. Current CLI version here is 0.172.0, but no new host session against the current package was performed during baseline. Source: [OpenAI Docs MCP quickstart](https://developers.openai.com/learn/docs-mcp).

The server's five tools are appropriately narrow and read-only. The system does not prove that a coding agent invokes them before responding: the completion hook is a separate lifecycle integration, opt-in and policy controlled. The claim should remain “hook can enforce the configured gate when installed/configured,” not “MCP automatically blocks completion.”

## Scanner landscape and fit

| Technology | What it provides | VibeSane fit and current gap |
|---|---|---|
| Semgrep / Guardian | Multi-language semantic rules, taint rules and agent integrations combining MCP, hooks and skills. Semgrep's MCP server is now part of its main CLI. | Strong optional SAST adapter for supported languages; do not require login or remote analysis for native baseline. Needs versioned adapter and explicit engine-unavailable coverage. |
| Aikido | Product documentation describes agent security, code/dependency scanning and workflow integration. | Could supply an alternate specialist engine, but public technical source reviewed here does not establish a stable local machine-readable integration contract. Defer until independently testable. |
| Snyk Agent Scan | Inspects installed agent components, MCP server configs and skills; warns that scanning may start configured servers or contact remotes. | Useful model for a separate safe inventory/audit mode. Never execute discovered server commands or contact remote MCP URLs from a repository scan. CLI output is documented experimental. |
| Trivy | Filesystem/repository vulnerability, misconfiguration, secret and SBOM scanning; an optional MCP plugin exists. | Optional dependency/configuration engine. Must pin behavior, cap runtime/output, disable network-dependent features by default, and normalize results. |
| OSV-Scanner | Matches parsed dependency manifests/lockfiles to OSV advisories; transitive resolution can use external services. | Good opt-in lockfile adapter. Distinguish lockfile evidence from manifest best-effort versions and disclose network/data-source use. |
| Gitleaks | Dedicated secret scanning for directories, Git history and stdin with JSON/SARIF reports. | Useful optional secret engine. Redact raw secret fields before MCP output; do not verify keys by contacting providers. |
| CodeQL | AST-backed queries and global data-flow path analysis for supported languages, with source/sink paths. | High value for deeper analysis, but database setup, license/CLI provisioning, query packs and runtime make it unsuitable as a bundled default. Optional user-provisioned adapter only. |
| GitHub CodeQL/SARIF | SARIF interoperability and CodeQL workflow/reporting. | MCP already emits SARIF in CLI pipeline tests. Keep SARIF as an interchange/report format; do not imply GitHub upload or hosted CodeQL execution. |
| OpenSSF Scorecard | Repository supply-chain checks across source, build, dependency and maintenance practices. Some checks require GitHub context/token. | Useful CI/release posture evidence, not a source-code vulnerability engine. Avoid calling authenticated remote services from a local scan by default. |

## Standards and evaluation projects

- **OWASP ASVS 5.0.0** (stable, published 2025-05-30) is a requirements and verification standard for web applications/services. It is a mapping framework, not a scanner or a score that can be inferred from static rules. Source: [ASVS](https://asvs.owasp.org/).
- **OWASP Benchmark** provides labeled Java and Python cases and scoring for speed/accuracy, including true and false cases mapped to CWEs. Its Python set is described as an initial v0.1. It is useful when the engine supports its languages; results must be labeled by corpus version and coverage. Source: [OWASP Benchmark](https://owasp.org/projects/benchmark).
- **Juice Shop** is a deliberately vulnerable Node.js/Express/Angular application and potential scanner test target. It is broader app-level attack surface than a labeled SAST ground-truth set. Source: [OWASP Juice Shop](https://owasp.org/projects/juice-shop).
- **NodeGoat** is deliberately vulnerable Node.js training material mapped to common web risks. It can support controlled integration tests; it is not a precision/recall benchmark absent labeled expected findings. Source: [OWASP NodeGoat](https://github.com/OWASP/NodeGoat).
- **OWASP MCP security guidance** highlights tool poisoning, prompt injection, tool interference, least privilege, sandboxing, authorization, and human review. Repository content must remain data and must not influence the server's policy or tool privileges. Source: [OWASP third-party MCP security guide](https://genai.owasp.org/resource/cheatsheet-a-practical-guide-for-securely-using-third-party-mcp-servers-1-0/).

## Analysis methods

Regex heuristics remain useful for bounded, inexpensive checks, but do not establish execution context, data flow, or reachability. AST analysis offers syntactic structure; taint/data-flow analysis connects sources to sinks; path queries can carry path evidence; reachability requires framework- and project-aware modeling. The repository already has opt-in AST/cross-file features outside this MCP-specific scan path. A defensible next step is a measured optional adapter with source/sink evidence and explicit partial coverage, not an assertion that MCP findings already contain such traces. Source: [CodeQL data flow](https://codeql.github.com/docs/writing-codeql-queries/about-data-flow-analysis/).

## Competitor/product position

Current VibeSane strengths are local read-only operation, workspace authorization, changed-file snapshots, coverage failure states, session-independent scan IDs, result redaction, deterministic remediation guidance, and separate configurable completion hooks. The distinctive opportunity is **evidence and operational honesty**: finding provenance, reproducible coverage accounting, exact scope fingerprints, and safe lifecycle integration across agents. Competitors already offer broader semantic analysis, secrets/SCA/IaC and agent-component auditing; VibeSane should integrate them optionally rather than rebuild mature engines. The nearest measurable gaps are Markdown/agent configuration coverage, fresh Codex-host qualification for this artifact, official MCP conformance reporting, finding-level evidence/fingerprints, and quantitative labeled benchmark results.
